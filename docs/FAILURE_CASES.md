# 我为什么从多阶段角色规划回到了 Scene RAG

我最初做这个项目，只是想让凯伊在日常聊天中表现得更像原作中的她。我希望她能够自然地回应眼前的事情，而不是机械地重复几句有辨识度的台词，也不希望角色扮演牺牲正常讨论数学、技术问题的能力。

这份记录按我实际经历的顺序写。对我来说，它并不是三四个孤立 Bug 的清单，而是一次关于 **RolePlay 中究竟应该把哪些信息交给模型** 的探索。最终版本并没有否定所有中间表示；我只是逐渐学会区分：哪里需要保留情境，哪里需要确定性的工程约束。

## 1. 起点：Scene RAG 已经能聊天，表情却总是太激烈

最早的系统其实相当简单：我将原作剧情整理成 Scene Card，通过 Embedding 检索相关场景，供模型参考，再由一个独立的 Sticker Selector 为台词选择角色差分。

当时一个特别明显的问题是**表情容易极端化，尤其容易选到愤怒表情**。台词本身未必真的表达愤怒，但 Selector 会把一些语气强烈、吐槽、抗议或害羞时的反应判得过重。

起初，我把修改任务主要交给 Codex，希望依靠半自动化开发解决问题。它会针对一次误判增加违禁词、触发条件或额外判断。这样做在局部可能有用，但接下来又会出现新的错误：相似的词在不同场景中有不同的含义，禁止了一种匹配，不等于系统学会了识别另一种情境。

我后来意识到，问题不只是规则不够完善。**选择表情所需要的语境，没有被正确地提供给 Selector。** 仅靠词面或者不断增长的例外清单，很难判断一个角色到底是在生气、害羞、故作强硬，还是开玩笑。

这件事使我第一次把注意力从修补输出转向了架构设计。

## 2. 我为什么尝试多阶段角色规划

为了更系统地理解问题，我开始和 ChatGPT 讨论 RolePlay 的设计，并阅读相关研究。显式建模情绪、行为动机和角色状态是一条很有吸引力的路线。我当时的想法也很自然：一个 Agent 不必把全部信息交给每一个模块，只需要让各模块完成自己的子任务，再把摘要和建议传给下一层。

因此，我在不同阶段尝试过 `Appraiser`、`Deliberator`、`State Manager`、`Speech Habit` 等组件。其中一条重要的思路是：

- `Appraiser` 解释当前事件可能引起的情绪与反应；
- `Trajectory` 根据召回的高相似度 Scene，生成值得模仿的互动建议；
- `Deliberator` 综合这些建议，确定角色接下来应该如何回应；
- `Generator` 根据最终建议组织可见台词。

这里说的历史 `Trajectory` 是**生成模仿建议的模块**，不是当前 Scene 数据中的 `trajectory_id`、`trajectory_order` 等来源顺序字段。旧模块也并非在每个版本中都同时存在。

这套分工在纸面上相当合理：上游负责理解，下游负责表达，还能分别检查每个模块的输出。但实际使用时，我逐渐发现一个矛盾：**Generator 可以准确执行 Deliberator 的建议，却仍然说出十分 generic、或者情绪过于极端的话。**

我现在更倾向于用“连续的有损抽象”解释这类现象。原作 Scene 里的情绪、口吻、互动节奏、关系距离以及各种难以命名的细节，被上游转换成“应该害羞”“先抗议再接受”“语气柔和一些”等粗粒度结论。中间步骤可能理解错，也可能总结得太笼统；即使建议完全符合接口，Generator 也已经看不到许多产生这些建议的依据。

我并不认为所有中间表示都没有价值。真正让我不满意的是：**一套原本为了帮助模型理解人物而存在的流水线，开始代替人物决定每一轮应该怎样表演。**

## 3. Speech Habit：总结口癖反而使口癖无处不在

Speech Habit 模块的初衷是改善角色的语言辨识度。既然原作中存在有特点的句式和口癖，把它们提取出来，在需要的时候召回，似乎比完全依赖模型的默认文风可靠。

但我在使用中逐渐感到，这种设计可能造成**过度提示**。

角色口癖并不是只要满足某个关键词就应该触发的动作。它在什么情境出现、使用哪种句式、强度有多大、是否只说半句，都依赖具体的上下文与关系状态。如果把这些细节浓缩为几条语言习惯，再专门作为提示交给模型，就很容易把“角色有时这样说”变成“角色这一轮应该这样说”。

结果是，模型看起来越来越努力地模仿角色，却越来越像在完成一份人格展示清单。我所期待的角色辨识度并没有随着这些规则的增加而同步提高。

这也是我说 Speech Habit 是一种有损压缩的原因：**它把完整互动里的情境和强度抽象为可重复执行的描述，而这些恰好可能是自然说话最重要的部分。**

这一观察后来成为我回退多阶段规划的理由之一：与其要求 Generator 每轮执行独立的口癖提示，我更希望让原始 Scene 里的互动方式承担这项工作。它不能保证每次都出现某种标志性表达，但对我而言，这反而更符合真实的对话。

## 4. 我先回退到 Scene-only，但 generic 和上下文稀释仍然存在

多阶段规划带来的问题让我决定先撤掉台词生成前的心理规划链。Generator 不再等待 Appraiser、Trajectory 和 Deliberator 把场景翻译为一份行为剧本，而是直接获得当前对话、角色卡及检索到的 Scene，由它自己决定这一轮说什么。

我把这个回退称作 **Scene-only**。它只表示台词生成不再由额外的心理规划模块逐层控制，并不是移除了角色设定、Memory、关系重排和知识检索。原作 Scene 也仍然只是互动先例，不会自动变成当前正在发生的事实。

**然而，回退并没有解决全部问题。** 我仍然会遇到 generic 的回复，而且 Scene 中那些细腻的语气、关系和互动方式，在完整 Prompt 里似乎容易被其他内容稀释。对我来说，这是一次重要的反例：如果只把问题归咎于 Appraiser 或 Deliberator，那么删除它们之后，角色就应该足够自然；但实际体验不是这样。

于是，我开始把注意力从“信息在模块之间怎样传递”，转向“Generator 最初接收到的角色信息是怎样写出来的”。特别是，我重新审视了那份仍然以外部视角分析人物的角色卡。

## 5. Scene-only 之后，我才改写第一人称角色卡

我保留了一份失败时期的角色卡：[`tendou_kei_legacy_schema_v1.yaml`](history/tendou_kei_legacy_schema_v1.yaml)。这是一份 **schema v1 的历史案例，不是现行运行配置**。现行 Profile 位于 [`roles/profiles/tendou_kei.yaml`](../roles/profiles/tendou_kei.yaml)。

这张旧卡能够反映我当时组织角色信息的方式：我把人物拆成 `personality.core_traits`、`motivations`、`contradictions`、`speech.verbal_habits`、`behavior.interaction_modes`，还使用了 `speech_habit_pack` 和显式的情绪、表达策略。例如：

```yaml
speech_habit_pack: tendou_keiv2

personality:
  core_traits: ["感情丰富但不自知，私人情绪经常外露", "关心细腻", "忠诚重情", "认真负责", "自尊独立", "吐槽直接", "理性敏锐"]

behavior:
  interaction_modes:
    official_duty:
      tone: "简洁、果断；优先处理事实、风险和责任，不进行无关的情绪表演"
```

有意思的是，**旧卡其实已经写了很多防止机械表演的提醒**，例如反应应由情境决定、不必每轮重演情绪、普通问答不必强行加入口癖。我继续添加这些限制，却仍然感到模型在完成“如何扮演凯伊”的外部分析任务，而不是直接以凯伊的身份交流。

我开始怀疑，问题不仅是内容的多少，还包括内容的**叙述立场与形式**。一份第三人称的人格分析可以在描述上很准确，却不一定是生成自然角色对话时最合适的上下文。它可能让模型优先处理“她具有什么特点、此刻应表现什么”，而不是从人物已有的经历、关系和对话中形成回应。

因此，**在回退到 Scene-only 之后**，我才重写了角色卡，让凯伊以第一人称讲述自己的经历、关系和自我认识；与此同时，将身份边界、来源与事实约束保留为独立的技术说明，而不是把所有指令都改写成角色自述。

这个修改之后，我在长期使用中明显感到角色更自然、更灵动，generic 和上下文稀释问题也有所缓解。这里记录的是我的实际体验，不是一次严格控制变量的实验。我也不认为单凭第一人称三个字就能解决问题：真正改变的是角色信息的组织和呈现方式。

## 6. 最后的转向：让 Sticker Selector 也参考场景

于是，我把从台词生成中学到的经验用于表情选择：不是继续增加愤怒词黑名单，而是让 Selector 尽可能看到当前台词及原作场景中对应的可见反应。

目前的实现由 Generator 为每个气泡附带一个临时 `affect`，用于描述已经生成的台词呈现了哪一类可见反应；Selector 再结合当前输入、台词、场景摘录和可用贴图说明选图。在 family 有效且素材标注完整时，候选会限制在相应的主 family；没有合适图片可以返回 `null`。

这个 `affect` 不是旧式心理状态机：**它描述已经写好的台词，不规定台词该如何写；不显示给用户，不持久化，也不在下一轮回灌。** Selector 同样不能反向改写 Generator 的文本。

从我的个人使用体验看，这次改变终于明显改善了早期最困扰我的选图问题。当然，Generator 如果一开始就判断错了 affect，或旧 Scene 的表情标注本身有问题，系统仍可能出错。这里我更在意的是修改的方法变了：我不再依靠一条条例外修补，而是让需要判断的模块获得完成任务所必需的场景信息。

## 7. 我最终学到的不是“模块越少越好”

最初我以为，更细致的模块分工会带来更细致的角色表达。后来我发现，对于生成自然台词这样高度依赖上下文的任务，过早把 Scene 抽象为标签和策略，可能让信息的表达方式和粒度与任务本身不匹配。

但贴图选择又说明，**适当的中间表示仍然十分有用**：它的输出空间是有限的、可以按 family 校验的贴图集合，和开放式的台词生成不同。我们完全可以为它使用轻量的 affect 描述及确定性的候选过滤，而不必重新构建一个负责角色心理规划的系统。

我目前更认可的原则是：**根据下游任务决定抽象的程度，让必要的信息抵达真正需要它的地方；不要让粗糙的行为摘要取代原本丰富的互动依据。**

我在[架构取舍](ARCHITECTURE_DECISIONS.md)中写下了一个条件分布视角，用来解释这条路线背后的想法。它是我理解问题的方式，而不是声称已经用数学证明 Scene RAG 普遍优于其他架构。
