# 失败模式、证据类型与复查路径

这里区分三种证据：**历史观察**是[开发手册](ROLEPLAY_DEVELOPMENT_MANUAL.md)对开发过程的记录；**机制分析**解释可能的因果链，尚非控制变量结论；**合成示例**只示范如何复查。未取得可复核的冻结包或历史实验原始日志，因此不报告 A/B 增益或错误率。

## 1. 人格理解变成逐条执行

**历史观察：**手册 §0.2.1–0.2.3、§18 记录了 State Manager、Appraiser、Deliberator、Speech Habit/Character NLG 与 Corrector 的尝试，以及频繁的“抗议—让步—解释—收束”和口癖模板化问题。这是作者的开发观察，未与单一模块做严格因果隔离。

**机制分析：**如果把“认真、害羞、嘴硬”都交给规划器作为本轮待展示项目，角色即使只需接受邀请，也可能逐项表演标签。第一人称自述把经历和关系作为理解材料，不要求每轮兑现所有特征。

**合成示例：**用户问“下午去散步吗？”失败回复先固定否认，再害羞让步，最后解释自己为什么这样说。复查时应比较同类邀请在不同上下文中的结构多样性，也检查人物辨识度是否保留。

## 2. 完整 Scene 被误当作一轮应演完的剧情

**历史观察：**手册 §0.2.4、§8.3、§18 记录了完整 Scene 用于保留前因后果，同时 Generator 应在对方可接话时停下来的取舍。历史记录描述了单回合情绪闭合风险，但没有提供可公开核对的量化对照。

**机制分析：**检索卡是一段已结束的互动；若模型将其叙事结构直接迁移到当前正在进行的聊天，容易在一条回复中完成惊讶、否认、接受、道谢和平复，留下很少接话空间。保持完整检索证据与限制当前话轮长度可以并存。

**合成示例：**用户说“给你留了点心。”失败回复一轮写完惊讶、收下、夸奖、安排下次回礼与离场。复查时既看是否留有自然接话点，也看是否遗漏当前必须回答的信息。

## 3. 旧 Scene 贴图标注诱导跨 family 误选

**历史观察：**手册 §5.1、§5.4、§9、§17 记录过玩笑式抗议被贴成 `kei_flustered_huff` 的旧标注问题；该贴图的主 family 为 `angry`，而对话中的可见反应可能更接近 `embarrassed`。手册示例中的历史台词已在公开副本中替换为合成句，原始卡不随包分发。

**机制分析：**Selector 若将 Scene 的旧 sticker ID 当指令、或在所有图片中平权竞争，可能把台词的强调力度误解为愤怒。当前流程先按 Generator 的可见 affect family 过滤；无同类可用图片时允许 `null`。旧标注仍应逐卡复核，family gate 不能修复错误的 Generator affect。

**合成示例：**角色轻声说“我会不好意思的”，却选到明显愤怒图。复查应分别记录 Generator affect、候选 family、Scene 标注和最终 ID，确认错误发生在哪一层。
