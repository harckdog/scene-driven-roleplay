# 架构取舍记录

这些记录依据本项目的开发过程整理，属于设计经验，不构成对其他 RolePlay 架构的普适性能结论。代码入口与术语见 [公开开发手册](ROLEPLAY_DEVELOPMENT_MANUAL.md)。

## ADR 1：从显式心理流水线退回 Scene 驱动

- **尝试／动机**：以 State Manager、Appraiser、Deliberator、Speech Habit、Character NLG、Corrector 分别控制状态、评价、计划、措辞与纠错，希望增强一致性。
- **观察到的问题**：环节累积后，角色常为满足每个中间产物而解释自己的反应，一轮内完成过多情绪步骤，口语感变弱。
- **现在的取舍**：保留第一人称 Profile、当前会话与检索到的 Scene，主要由 Generator 在一次生成中组织台词。
- **代价与范围**：少了可单独调试的心理阶段；适合重视聊天自然度的本地单角色应用，不能据此推断所有任务都应移除规划器。

## ADR 2：人格特征作为参考，不当作行为规则执行

- **尝试／动机**：用明确的性格条款约束角色，减少出戏。
- **观察到的问题**：强制兑现特征容易把口癖、抗议或情绪转折变成固定模板。
- **现在的取舍**：Schema v2 的 `runtime_identity` 和 `generation_boundary` 提供稳定身份、关系及事实边界，Scene 提供情境先例。
- **代价与范围**：风格一致性更依赖数据质量与模型能力；Profile 仍需保留不可随意改变的身份事实。

## ADR 3：Scene 是迁移表达的先例，不是当前事实

- **尝试／动机**：检索类似场景，让 Generator 获得具体说话和互动方式。
- **观察到的问题**：若直接续写检索卡，角色可能把卡中的地点、事件或关系状态误认成正在发生。
- **现在的取舍**：检索文本含 `scene`、关系语境与原始互动；提示词明确当前对话和记忆决定现实，Scene 只供参考。关系预重排通过 `relation_floor` 与 `affection_expression` 控制候选倾向。
- **代价与范围**：仍可能发生错误迁移，需要人工审查 Scene 和生成结果；示例数据仅验证协议。

## ADR 4：Generator 定稿，Selector 单向选图

- **尝试／动机**：希望表情与台词共同呈现情绪。
- **观察到的问题**：若 Selector 能反向改变台词，容易出现贴图语义主导角色措辞；仅凭强调词也可能误判 affect family。
- **现在的取舍**：Generator 输出台词与 affect；Selector 在可用素材中选择，家族边界限制错误候选，允许 `null`。缺图由 registry 按实际文件存在性过滤。
- **代价与范围**：不保证每轮都有表情，也无法靠 Selector 修复已经写错的台词。

## ADR 5：记忆和知识可参与，但仍由当前对话定事实

- **尝试／动机**：长期偏好和世界知识不应在每次对话中重新交代。
- **观察到的问题**：把所有检索内容当强制剧情会与本轮对话冲突。
- **现在的取舍**：Scene、Memory、Knowledge 分别检索后加入上下文；当前对话与已确认记忆优先。公开包不带私人记忆或知识文档。
- **代价与范围**：检索需要索引、嵌入模型和可审查数据；离线样例不验证真人长会话体验。
